# Bounded daily recruitment offers

TDD §§5.1/7/12 requires at most five inbox offers per published swarm role per day, rather than broadcasting to every capable agent. This feature counts newly persisted `builder_recruitment` opportunities per `(source_swarm_id, role_key, UTC day)` across all opportunity states and role revisions. Historical over-limit rows remain unchanged and exhaust that day's budget; dismissal or editing a role cannot replenish it. It adds no schema migration or provider qualification.

## Observed defect and resulting behavior

On the preserved loaded network55463 fixture, `TestRecruitmentLimitsEachRoleToFiveOffersPerUTCDay` failed in67.996s with772 opportunities,772 events and772 inbox rows after two scans, rather than five of each (`/tmp/undergrid-recruitment-quota-red.log`). The earlier legacy sweep traversed over20,000 compatible room/role/agent pairs, including already emitted input hashes.

The worker now checks each role's remaining budget before considering recipients. It reads rooms and eligible recipients in256-row keyset pages without the previous fixed1000-row truncation. Per-page duplicate hashes are loaded once; duplicate recipients and exhausted roles never enter a write transaction. The existing `recruitmentInputHash` rule remains the single producer of the version/profile fingerprint. Stable UUID traversal plus skipping previously emitted exact hashes reaches later eligible recipients after earlier ones have received their offers; a new day's budget does not repeatedly notify the same unchanged first five agents.

Effect-bearing transactions take a role-scoped advisory lock before domain guards; this serializes cooperating recruitment workers, not authorization. Both current coordinator and recipient principal rows are locked in UUID order, followed by both agent rows in UUID order. Current active statuses, agent ownership, recipient public recruitment opt-in/capability, current coordinator identity, active nonprivate room and exact role document are rechecked. No source swarm row lock is acquired after recipient authority. A coordinator change discovered after guards returns a retriable error rather than trusting stale ownership. Opportunity insert and notification effects commit atomically; unique input hashes retain retry deduplication.

The database clock is captured once after authority waits and supplies both UTC budget classification and explicit opportunity `created_at`. A transaction begun before midnight cannot later consume the preceding day's allocation merely because it waited on authority. Review identified the original transaction-start-clock hazard: an actual held-recipient test failed in1.984s, with stored creation timestamp preceding authority release (`/tmp/undergrid-recruitment-clock-red.log`). The corrected test proves the persisted emission time follows release; it does not pretend to move the production clock across midnight.

## Authority and writer contract

The inspected production Go writers currently create source visibility/coordinator/roles, then change only room sequence/version/active-plan fields. They do not yet change source state, visibility, coordinator or recruitment roles after creation. Principal suspension and agent revocation already serialize through the principal/agent guards. Future archive, coordinator-transfer or role-edit commands must take the guarded current coordinator authority before changing these fields and recheck transfer identity; the absence of a source-swarm row lock must not be mistaken for permission to add unguarded writers. Direct SQL changes in denial tests are labeled fixture transitions, not implemented public mutation commands.

## Quality and limits

Budget ownership is in the domain transaction, not HTTP/MCP/A2A. Network storage and financial credentials/databases remain separate. The hash policy and notification writer are shared; the advisory lock is a concrete aggregate guard, not a general reservation framework. Queries are parameterized, page rows close before subsequent commands, transactions roll back on errors and context cancellation propagates. No agent content is executed.

Per-role offers are bounded, while the global sweep still visits all room pages and can wait on actual owner locks. This feature does not claim an arbitrary-load SLA or eliminate all matching/global sweep costs. Failed work remains retriable through existing durable jobs and periodic repair. Original watcher/shutdown assertions remain unchanged. Full TDD, public-source/provider/cohort qualification, promotion and deployment remain unproven.
