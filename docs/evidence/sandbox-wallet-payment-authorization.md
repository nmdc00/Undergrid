## Resulting behavior

POST `/v1/payments/{id}/wallet-authorization` requires the financial credential's `payments:authorize` scope, original quote credential, `Idempotency-Key`, exact `quote_hash`, `chain_id`, `token_address`, `signature`, and `authorization` containing `from`, `to`, string `value`, string `valid_after`, string `valid_before` and bytes32 hex `nonce`. The payment must already have its separate owner-policy reservation (`authorized`). Owner EOA control proof, server quote signature, owner spend policy/reservation and external payer EIP-712 signature are separate gates.

The command runs under the existing actor/credential locks and rechecks live credential, original credential, current policy version/period/product/payee/asset/expiry and immutable original wallet binding. It verifies standard `TransferWithAuthorization` EIP-712 signatures against that payer, Base Sepolia84532, the pinned native USDC token, exact original payee, quote nonce and quote expiry (Unix seconds). `valid_after` is exactly string `"0"`; `valid_before` is the quote's expiry second. The window uses EIP-3009 strict inequalities.

Transfer `value` is **Amount + Fee**, paid to the same configured platform payee, exactly matching the already reserved gross. The signed quote retains both itemized fields. Future x402 `required.amount` must use this gross; future receipt/effect/refund processing must account for actual gross once. No split-payment or separate fee transfer is introduced. USDC gross values exceeding uint256 are rejected before quote creation and authority checks without truncation; the maximum valid gross is accepted.

The authorization and request hash/key are immutable typed columns on the existing financial payment aggregate (migration010). Identical original command retries/restart recover one record; altered content/key cannot replace it. There is no second reservation or financial effect. GET payment returns the original normalized authorization only within the existing actor RLS.

USDC dispatch now requires both the public-only server-quote verifier and the persisted independently verified payer authorization. A missing proof returns unauthorized while preserving the separate existing policy reservation, so the payer can still provide proof. Revocation, stale wallet/policy, expiry or invalid proof fail before submitting. An already submitting/unknown attempt retains its original quote, payer authorization, provider key and reservation after wallet rebinding; identical retry recovers it and redispatch stays rejected. This is the Undergrid dispatch gate, not an on-chain revocation or nonce-state check. Stripe behavior stays separate.

API startup additionally requires explicit trusted `UNDERGRID_SANDBOX_USDC_TOKEN_NAME` and `UNDERGRID_SANDBOX_USDC_TOKEN_VERSION`. Public-only worker Stores use `WithUSDCVerification` and `WithUSDCTokenDomain`; they need no issuer private key or wallet private key. Name/version are copied into each immutable authorization. Fixtures use name `USDC`, version `2` as configured assumptions, not verified token-contract metadata. This REST command is not a complete x402 PAYMENT-SIGNATURE transport; the future adapter must map its fields to that protocol's camelCase payload.

## Primary protocol inputs

[EIP-3009](https://eips.ethereum.org/EIPS/eip-3009) was fetched on14 October2026. Typed hashing follows its EIP-712 domain and `TransferWithAuthorization` fields; EOA recovery enforces valid scalars, low-S and supported recovery parity. Existing EIP-191 owner-control recovery shares only the validated EOA digest-recovery primitive; the two signing preimages remain distinct.

The official [x402 exact EVM specification](https://github.com/coinbase/x402/blob/dd927a26cfefc98c24b3ec38b3a8f204dad0c60d/specs/schemes/exact/scheme_exact_evm.md) was fetched through GitHub's contents API at commit `dd927a26cfefc98c24b3ec38b3a8f204dad0c60d`. Its EIP-3009 branch requires a transfer authorization signature; full verification additionally needs balance/nonce/capability checks and simulation, and settlement is a separate facilitator operation. This implementation claims local EOA signature and exact quote authority only.

## Pragmatic review and limits

Gross calculation has one financial-domain helper used before minting and authority verification. The HTTP route calls the checked domain command; worker dispatch reuses persisted-proof verification under the same actor lock. SQL shape/immutability constraints independently defend stored contracts and NULL semantics. Recovery reuses the existing credential-scoped idempotency aggregate and actor lock, without extra tables or charge effects. Database failures propagate rather than being mislabeled authority denial; payment loading avoids an extra common-path query. No generic custody/fee/keystore framework, network-domain dependency or arbitrary agent execution was added.

No wallet private key is stored by the service. Test EOA keys and typed signing are fixture-only. Contract name/version/decimals, code/capability, balance, nonce use/cancellation and transfer simulation need independently qualified RPC/provider proof. No facilitator call, chain transaction, canonical nonce→transaction receipt, finality/reorg handling, external refund, paid label, production deployment or provider qualification is claimed. Those remain required subsequent TDD slices and explicit external gates.
