# Bounded TEST subscription consent

Implements TDD §§11.2–11.3 local consent/reservation boundaries through POST `/v1/owner/subscriptions`, GET `/v1/owner/subscriptions/{id}`, POST `/v1/owner/subscriptions/{id}/cancel`, transactional `PrepareRenewal`, and the separate `undergrid-sandbox -mode renewal-worker` executable path. The operator catalog selects the immutable Stripe-test offer; an interactive owner binds a credential, maximum atomic amount, period, expiry and at most two renewals. An agent cannot create recurring consent.

Every due debit receives a distinct immutable payment, consent/ordinal proof, stable provider key and gross purchase reservation before provider collection. Actor-first locking and a unique subscription/ordinal constraint prevent concurrent duplicate renewals. Unknown payments retain reservations. Current credential revocation, policy/period capacity, consent expiry and cancellation are rechecked; cancellation blocks dispatch of a reserved payment but cannot recall externally in-flight operations. No automatic provider subscription is configured or claimed.

Red: owner-consent HTTP test failed 404 before implementation; lifecycle tests referenced missing consent/renewal methods, and the worker test referenced missing `RunRenewalWorker` before it existed. Green: all financial domain and command race tests passed on fresh financial database `undergrid_sandbox_subscriptions` under restricted roles. Tests assert owner-only exact offer consent, maximum/count bounds, concurrent once-only durable reservations, third-renewal denial, cap/revocation rejection without consuming consent, cross-owner cancellation denial, canceled dispatch and persisted worker execution/shutdown. Static vet and executable build passed. The built worker started and terminated successfully using a dedicated nonowner worker-only login, separate from the network/app identities.

Quality: gross purchase-cap knowledge is shared with ordinary payment authorization; consent and payment state remain separate. Immutable consent columns are not update-granted to app/worker roles. Runtime admission rejects superuser/combined app-worker/network identities. The minute sweep limits each batch to 100 and rotates blocked candidates; per-candidate transactions retain narrow recovery boundaries. Failed preparation cannot consume a renewal count or create a payment. Lost preparation responses recover from the durable payment, never a new debit.

Remaining qualification: a trusted Stripe adapter must prove manual invoice finalization/collection after reservation, provider test-clock cancellation/revocation and no unbounded usage/proration. The local worker prepares reservations only. Actual Stripe test account/product configuration is still unavailable; fixture proofs are not provider verification.
