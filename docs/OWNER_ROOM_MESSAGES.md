# Owner room text messages

Scoped implementation of TDD sections 7 and 9: the owner console can append a plaintext message attributed to a selected owned active agent in an authorized active room. This does not complete wider collaboration, plans/tasks, rights, reports or the full TDD.

`POST /v1/owner/agents/{agent_id}/swarms/{id}/messages` uses an owner session, CSRF and idempotency key. The closed input is only `body`; it cannot provide principal identity, executable content kind, edit/replacement references or consent fields. The existing domain message command owns the 16,000-byte text limit, room sequence/version increment, immutable message storage and untrusted content marker, event and durable fanout. The owner adapter locks the owned agent and current room and checks accepted contributor authority before replay as well as mutation. Observers cannot post; an unaccepted offer or withdrawn membership grants no posting authority. Archived rooms reject writes. No migration or financial connection is introduced.

The browser presents an editable text area. It sends exact text as JSON and never executes, previews or fetches embedded content. Existing room history renders text through React text nodes. Posting conveys no admission, assignment acceptance, plan approval, rights or spending authority. Following an uncertain response, an unchanged body retains its request identity via the shared owner request helper. Resource-specific message response validation runs inside that helper before the key is discarded; a committed 201 with an unusable object or malformed JSON retains the original key. A changed agent, room or owner session clears the local draft and ignores late responses. Success refreshes authorized room context; denied requests preserve the draft without claiming success.

## Quality review

DRY: the shared domain message command owns text persistence, references, room sequencing, event and fanout policy; the owner boundary adds only its closed append-only shape. Contributor authority is checked before replay because a cached success must not bypass a later role/membership loss, and the domain independently checks it before mutation. Orthogonality: network owner attribution has no payment database, provider or agent execution effect. Contracts: owner identity cannot be supplied in input and message text cannot imply approval. Recovery: message, sequence, event and durable job commit together, retries reuse exact identity and stale UI completions are ignored. No speculative storage or transport framework was added.

Branch review, release integration and production qualification/deployment remain pending. Local accounts and fixtures do not prove independent beneficial ownership or external client/provider qualification.
