# Coordinator succession implementation contract

TDD §7.3 permits existing principals to propose a successor after the coordinator disappears, with unanimous currently required contributor/acceptor approval. Succession changes governance only: it never accepts an assignment, changes plan/rights, marks work complete, grants private history to an outsider or revokes an existing license. Silence and timeout are not consent. A required absent party can legitimately prevent succession; the documented permitted-export fork remains the exit rather than an administrative bypass.

Planned entrypoints are `POST /v1/swarms/{id}/coordinator-proposals`, `GET /v1/coordinator-proposals/{id}`, and versioned `POST /v1/coordinator-proposals/{id}/approvals` and `/accept`. A current accepted contributor may propose an eligible accepted contributor as successor. Exact-hash principal votes and the nominated agent's separate explicit acceptance are required. Proposal creation binds the source room version; subsequent proposal actions bind the immutable proposal revision and require Idempotency-Key. Replays recover their original authorized result without repeating events, while changed payload/precondition conflicts. Current membership and credential authority apply even on replay.

The electorate is the accepted plan's exact required contributor and acceptance-principal sets, with current accepted membership checked, plus the successor principal. Without an accepted plan, accepted contributor-role principals and the successor principal are required. Holding the coordinator office alone does not create a veto, but an old coordinator named as a required plan party cannot be removed from consent. Membership identity/role/version, accepted-plan hash/head, relevant policy versions and successor identity are snapshot inputs. Changes invalidate the proposal rather than silently recomputing its approvers. Deadlines expire pending proposals without transferring authority.

New explicit `coordinator:propose`, `coordinator:approve` and `coordinator:accept` scopes are proposed; approval/acceptance additionally require an explicit live owner policy opt-in for coordinator succession. Existing rights-template acceptance does not implicitly authorize governance. Approval and acceptance remain separate even when the same principal controls several agents. Each required principal votes once, and the nominated exact agent must accept.

The source transition must obey the recruitment guard contract: before actor/room locks, acquire relevant current room authority principal rows in UUID order, then agent rows in UUID order. Recheck current coordinator and snapshot under the room lock; transfer updates coordinator and the old/new membership roles/versions atomically with proposal state, votes, events and inbox work. No source swarm lock may be introduced after a recipient authority lock in recruitment. The pre-auth helper must expose no room metadata or lock arbitrary foreign rooms for an unauthorized caller. A coordinator identity change while acquiring guards fails/retries instead of proceeding under stale locks.

Network migration027 is reserved if normalized proposal/vote persistence is required. Existing plan approvals cannot represent this distinct purpose by fabricating a plan or attaching succession consent to a rights grant. Public REST contract, finite MCP/A2A command registry and UI will expose the actual supported workflow after its domain proof. Archive, assignment replacement and source-policy changes are separate features.

This document records implementation planning. Runtime code and migration are not implemented by writing this contract; behavioral HTTP/PostgreSQL tests must first demonstrate the missing behavior. Root's current full-release gate owns network55463, so no competing persistence/timing tests run until it is terminal.
